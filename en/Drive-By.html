1. Installing the addon

Before configuring anything you need the addon loaded in the Arma Reforger Workbench.

Prerequisites

  • Arma Reforger + Arma Reforger Tools (the Workbench) installed.
  • A project/mod already created in Workbench, or the SHS Drive By addon folder placed in your addons directory.

Steps

  1. Place the SHS Dive By folder inside your Workbench addons directory (e.g. ...\My Games\ArmaReforgerWorkbench\addons\SHS Dive By).
  2. Open Arma Reforger Tools → Workbench and load the project that contains the addon.
  3. Let the Script Module compile. Watch the console — if any script fails to compile, the entire drive-by system is disabled (no seats, no logs). Fix compile errors before continuing.
  4. In the Resource Browser, confirm the addon's prefabs and scripts appear under the SHS Dive By source.
  5. Load a world with a supported vehicle and verify the extra "Get in" (Gunner) action shows on a drive-by seat.
Verifying it's alive While you control your character the system prints a heartbeat to the console every ~2 seconds ([SHS Monitor] …). If you see the heartbeat, scripts compiled and the seat manager is running. Entering a drive-by seat then prints [SHS DriveBy] ToSlotState …. No heartbeat at all means a script failed to compile.
OneDrive warning If this addon lives in a OneDrive folder, files-on-demand can serve stale or partially-synced copies to external tools, which looks like a "truncated" script. If a file appears cut-off, confirm it directly in Workbench before assuming it's corrupt.

2. How the system works

A drive-by seat is not a new component. You override a vanilla vehicle (or seat) prefab and inject data into two components that already exist up the inheritance chain. Reuse their existing instance GUIDs — never fabricate a second copy of either, or the vanilla seats get clobbered.

ComponentRole
SCR_BaseCompartmentManagerComponentTags a vanilla seat slot with a shoot-seat ID.
ActionsManagerComponentHolds the extra "Get in / Switch seat (Gunner)" action (PS_ShootingSeatAction) that puts you in the shooting pose.

The link between them is the shoot-seat ID: the action's m_iShootSeatId must equal the compartment slot's m_iShootSeatId_PS. That pairing lets the code find the underlying seat (for door opening and occupancy checks).

There are two kinds of drive-by seat:

  • Pattern A A drive-by version of an existing vanilla seat. Uses a real compartment slot, a matching m_iShootSeatId, and the seat's existing aim context.
  • Pattern B A brand-new standalone shooting position (e.g. the M998 rear bench "gunner" spots). No compartment slot, no shoot-seat ID; you define its own aim context and enter it by switching seats.

3. Create the override prefab

Do this in Workbench so the .meta and inheritance GUIDs are generated correctly — hand-typing resource GUIDs is the #1 way to break an override.

  1. In the Resource Browser, find the vanilla prefab you want drive-by on — the whole vehicle prefab or its seat/compartment sub-prefab.
  2. Right-click → Create Prefab Variant / Inherit into SHS Dive By/Prefabs/Vehicles/…, keeping the same folder layout as the existing UAZ/M998 overrides.
  3. Open the new override and add the two component blocks described below.

Reference files already in the addon — the result should look like these:

FileShows
UAZ469_base.etOne Pattern A seat (simplest).
UAZ469/VehParts/Seats/UAZ469_seats_rear.etThree Pattern A seats on a seat sub-prefab.
M998_covered_base.etThree Pattern A seats + two Pattern B seats.
GUID rule The .et header Vehicle : "{GUID}path" is what the override inherits from; the .meta Name "{GUID}path" is its resource identity. Let Workbench set these — copy the shape from the working files, not the raw GUIDs.

4. Component 1 — SCR_BaseCompartmentManagerComponent

Re-declare the component by its existing instance GUID (find it in the vanilla prefab; both wheeled examples use {20FB66C5DCB8DF72}, but confirm per vehicle). List each vanilla seat slot you want drive-by on and give it a unique shoot-seat ID:

SCR_BaseCompartmentManagerComponent "{20FB66C5DCB8DF72}" {
 CompartmentSlots {
  CargoCompartmentSlot Passenger_r01 {
   m_iShootSeatId_PS 1
  }
  CargoCompartmentSlot Passenger_l02 {
   m_iShootSeatId_PS 2
  }
 }
}
  • Passenger_r01, Passenger_l02, … must be the exact vanilla slot names from that vehicle's compartment manager.
  • m_iShootSeatId_PS is any unique positive integer per seat (1, 2, 3 …).
  • Pattern B seats get no entry here — they have no vanilla slot.

5. Component 2 — ActionsManagerComponent

Re-declare it by its existing instance GUID (differs per vehicle; UAZ/M998 use {C97BE5489221AE18}). It has two sub-blocks: ActionContexts (Pattern B only) and additionalActions (one entry per seat).

5a. ActionContexts Pattern B

A new standalone position needs its own aim context — a new unique GUID, a ContextName, and a Position offset (the aim origin / where the prompt appears, relative to the vehicle):

UserActionContext "{6203372B06F9FFDC}" {
 ContextName "Passenger_r3"
 Position PointInfo "{6203372B1452F535}" {
  Offset 0.8283 1.2627 -1.7927
 }
}

Pattern A seats reuse the vanilla seat's existing context, so they need no ActionContexts entry — unless you want to nudge the aim origin, in which case re-declare the vanilla context by its GUID and set a Position (this is what UAZ469_seats_rear.et does).

5b. additionalActions — the PS_ShootingSeatAction

One per seat. This is the actual drive-by action. Each action and every PointInfo inside it needs its own unique instance GUID. This block is copied verbatim from the working UAZ469_base.et — the minimal complete Pattern A seat:

PS_ShootingSeatAction "{620F5A9F9335C042}" {
 UIInfo SCR_ActionUIInfo "{6208A45F7FD3AE71}" {
  Name "#AR-UserAction_GetIn"
  Icon "{04EF6B438A9F69A1}UI/Textures/UserActions/getinaction.edds"
 }
 ParentContextList {
  "passenger_r01"
 }
 Duration 0.5
 CanAggregate 1
 m_EntitySlotInfo PS_EntitySlotInfoSeat Seat {
  PivotID "codriver_idle"
  Offset 0 0.0687 0
  m_iShootSeatId 1
  m_LeftLegPointInfo PointInfo "{620F70FAE021FA78}" {
   PivotID "codriver_idle"
   Offset -0.1592 -0.2428 0.4355
  }
  m_RightLegPointInfo PointInfo "{620F70FAE32B1C0A}" {
   PivotID "codriver_idle"
   Offset 0.0725 -0.2489 0.4412
  }
  m_ExitPointInfo PointInfo "{620F70FAE48D0D00}" {
   PivotID "codriver_idle"
   Offset 1.0345 -0.9392 0
   Angles 0 90 0
  }
 }
}

6. Field reference

PS_ShootingSeatAction

FieldMeaning
UIInfo … Name#AR-UserAction_GetIn shows as "Get in"; the script auto-swaps it to "Switch seat" + "Gunner" when you're already in the vehicle.
ParentContextListThe context this action attaches to. Pattern A: the vanilla seat's context name (lowercase in the examples, e.g. "passenger_r01"). Pattern B: the ContextName you defined. Must match exactly, casing included.
DurationAction hold time (0.5 everywhere).
CanAggregateLeave 1.
m_EntitySlotInfoThe seat definition — see below.

PS_EntitySlotInfoSeat

FieldMeaning
PivotIDBone/pivot to anchor to. Set for Pattern A (ride the vanilla pose, e.g. codriver_idle). Omit for Pattern B so offsets are vehicle-relative.
OffsetX Y Z seat position relative to the pivot (or vehicle, if no pivot).
AnglesFacing, pitch yaw roll. Turn a bench gunner outward (M998 rear uses 0 -122 0 / 0 20 0).
m_iShootSeatIdPattern A: must equal the m_iShootSeatId_PS on the matching slot. Pattern B: omit (defaults to 0 = standalone).
m_bAllowBigWeapon1 = allow launchers / big weapons. 0/omit = rifles & pistols only (a launcher is force-unequipped and can't fire). Set 1 for gunner seats.
m_LeftLegPointInfo / m_RightLegPointInfoLeg IK placement (own PointInfo + GUID each).
m_ExitPointInfoWhere you're dropped on exit — own Offset + Angles. The script floor-clamps this, so approximate is fine.

Other attributes exist (m_fFallAcceleration = collision-damage eject threshold, m_fBendMultiplier, m_fRotationClamp, m_fFallAngle) with sensible defaults; leave them unless tuning.

7. The ID-matching rule (Pattern A)

This pairing must be exact, or the seat won't link to its compartment:

Compartment slot   CargoCompartmentSlot Passenger_r01 { m_iShootSeatId_PS 1 }
                                                                          |  (equal & unique)
Action seat        m_EntitySlotInfo ... { m_iShootSeatId 1 }  <-----------+

Every Pattern A seat is one slot entry (Component 1) + one action (Component 2) sharing the same ID. Pattern B seats have neither — just an action with its own context.

8. Firing rules (why a seat might not shoot)

The seat manager manages your fire input each frame:

  • Big weapons: a rocket launcher is blocked (and unequipped) unless m_bAllowBigWeapon 1. Machine guns, rifles and pistols fire normally.
  • Grenades / mines: always blocked from being thrown/fired while seated.
  • Weapon obstruction: if the muzzle traces into the vehicle's fire-geometry, fire is cut and the weapon lowered. If a new seat "raises but won't shoot," rotate/offset it so the muzzle clears the body.
  • Rotation clamp: aim is clamped ~120° off the seat's forward. Face the seat the way you expect to shoot.

9. Per-vehicle checklist

  1. Create the inherited override in Workbench (Section 3).
  2. Get the vanilla slot names and the instance GUIDs of both components from the vanilla prefab.
  3. Re-declare both components by those GUIDs — do not create new ones.
  4. Pattern A per existing seat: add CargoCompartmentSlot … { m_iShootSeatId_PS N } + a matching PS_ShootingSeatAction with m_iShootSeatId N, pointing ParentContextList at the vanilla context.
  5. Pattern B per new position: add a UserActionContext (new GUID + ContextName + Position) + a PS_ShootingSeatAction pointing at that ContextName, no shoot-seat ID.
  6. Give every new action and PointInfo a unique instance GUID.
  7. Set m_bAllowBigWeapon 1 on any gunner/heavy-weapon seat.
  8. Load in Workbench; tune Offset / Angles / leg / exit numbers until the pose sits right and the muzzle clears the body.

10. Pitfalls (learned the hard way)

Never duplicate a component Do not add a second ActionsManagerComponent or SCR_BaseCompartmentManagerComponent. Reuse the inherited GUIDs — a duplicate wipes the vanilla passenger seats.
  • The .meta must carry the correct resource GUID or the override won't apply — let Workbench generate it.
  • Duplicate/placeholder GUIDs on actions or PointInfos cause silent breakage; each must be unique.
  • A truncated or brace-unbalanced script anywhere fails the whole addon's script module (no drive-by, no logs).
  • Don't hijack the character command handler with a no-op scripted command to stop falling — it also freezes aiming and firing. Drive the pose with the SeatOnVehicle animation variable and leave the normal command running.
  • OneDrive can serve stale partial copies of files to external tools — verify in Workbench if a file looks cut-off.
